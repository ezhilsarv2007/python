About the Project

Software Release Risk Scoring System – A Python-Based Approach for Assessing Software Release Risks

1. Project Overview

The Software Release Risk Scoring System (SRRSS) is an academic engineering project developed using Python, Flask, and SQLite. It is designed to solve a fundamental challenge in the software engineering lifecycle (SDLC): evaluating whether a planned software build is sufficiently stable, verified, and safe to deploy into a production environment.

The system provides two powerful assessment pathways:

  • Static Code & Project Upload Analysis: Developers can upload complete project repositories (.zip) or individual source files (.py, .js, .ts, .java, .c, .cpp, .html, .css). Real static code analyzers (Python AST, Pyflakes, and Bandit-equivalent security rules) inspect the code without execution, detecting syntax errors, undefined variables, buffer overflows, and security vulnerabilities.
  • Manual Quality Parameter Assessment: Teams can evaluate 8 high-level software quality dimensions (unresolved bugs, blockers, code churn, test completion, performance, code quality, security, and documentation) with predefined weighted scoring.

2. Static Code Analysis Architecture

The static analysis engine inspects code structure and patterns safely without running or installing arbitrary third-party packages:

Python (.py) Analysis

Uses Python's standard library ast parser to verify syntax integrity, pyflakes to detect undefined names and unused imports, and security visitors to flag eval(), exec(), shell=True, weak hashes, and hardcoded secrets.

JavaScript / TypeScript (.js, .ts)

Inspects bracket and brace balance, flags dangerous eval(), XSS vulnerabilities via innerHTML, leftover debugger; statements, and hardcoded tokens.

Java (.java)

Checks class and method brace integrity, flags swallowed empty catch blocks, deprecated Thread.stop(), and unclosed I/O streams.

C / C++ (.c, .cpp, .h)

Identifies dangerous C11-obsolete functions like gets(), unbounded string operations (strcpy(), strcat(), sprintf()), and missing header include guards.

HTML Markup (.html, .htm)

Audits standard compliance (<!DOCTYPE html>), detects inline script event handlers (CSP hazards), missing image alt attributes, and deprecated presentation tags.

CSS Stylesheets (.css)

Checks CSS declaration block balance, flags overuse of !important that breaks specificity, and detects empty dead-code rulesets.

3. Working Methodology & Mathematical Scoring Model

The risk engine computes the overall release risk score using a linear weighted aggregation model. Each parameter \(i\) produces a normalized sub-score \(S_i \in [0, 100]\), which is multiplied by its predetermined weight \(W_i\). The sum of all weights equals 1.0 (100%):

Total Risk Score = ∑ (SubScorei × Weighti)
Parameter Assigned Weight Scoring Logic Rationale
Critical Blockers 20% (0.20) 0=0, 1=50, 2=80, 3+=100 pts Syntax errors and critical vulnerabilities will halt execution in production.
Security Issues 20% (0.20) 0=0, 1=40, 2=70, 3+=100 pts Security flaws expose applications to breaches, injection, and compliance failure.
Test Completion 15% (0.15) Risk = 100 - Completion % Unexecuted tests conceal regression bugs across untouched modules.
Unresolved Bugs 15% (0.15) min(Bugs × 6, 100 pts) High defect volume degrades user experience and product reliability.
Modified Code Files 10% (0.10) min(Files × 2.5, 100 pts) Substantial code churn raises the likelihood of unintended side-effects.
Performance Status 8% (0.08) Good=0, Average=50, Poor=100 High latency and throughput bottlenecks impact production scale.
Code Quality 7% (0.07) Good=0, Average=50, Poor=100 Poor maintainability and high complexity impede rapid bug fixing.
Documentation Status 5% (0.05) Complete=0, Incomplete=100 Missing runbooks or release notes impede deployment and incident recovery.

Risk Classification Thresholds:

  • 0 – 30 (LOW RISK): Safe to proceed with release following standard automated sanity verification.
  • 31 – 60 (MEDIUM RISK): Conditional release. Requires resolution of pending bugs and QA lead sign-off.
  • 61 – 100 (HIGH RISK): Release blocked. Immediate deployment must be aborted until critical blockers and vulnerabilities are resolved.

4. Technologies Used

Python & AST

Powers backend parsing, Abstract Syntax Tree inspection, file handling, and math algorithms.

Pyflakes & Bandit

Performs linter checks for undefined names and security checks for unsafe operations.

Flask (Web Framework)

Handles routing, multipart file uploads, session messages, and template rendering.

SQLite (Database)

Relational database engine with tables for manual assessments and code analysis logs.

ZipFile & Safe Extraction

Extracts project archives safely with Zip Slip path traversal defenses and size guards.

HTML5, CSS3 & Chart.js

Clean, student-oriented styling, responsive tables, and interactive risk progress meters.
